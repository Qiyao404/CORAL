# 错题集（Regression Ledger）

> **目的**：同样的 bug 不犯第二次。每条记录 = bug → 根因 → 教训 → 防回归检查。
>
> **使用规则（修 bug 必读）**：
> 1. 修任何 bug 前，先搜本文件确认是否已有同类教训（根因模式匹配）
> 2. 修完 bug **必须**在本文件登记一条（含回归测试位置），并在提交信息引用编号 `REG-xx`
> 3. "防回归检查"列是每次改对应模块时的自查清单
>
> **登记标准**：满足任一即登记——① 修了超过 30 分钟的 bug；② 根因涉及协议契约/状态机/异步时序；
> ③ 用户实测发现（非测试发现）；④ 同类问题第二次出现。

<a name="reg-01"></a>
## REG-01 · stream() 丢失 tools（P0，审查发现）

**现象**：Free 模式 agent 的工具调用一直"正常"，但 DeepSeek 频繁产生 `llm_degraded`（DSML 文本式工具调用）。
**根因**：`openai-compat.ts` 的 `complete()` 有 tools 映射、`stream()` 漏了 —— agent loop 主路径走 `chatStream` → `provider.stream`，**模型从未收到过 function 定义**，靠训练记忆以 DSML 文本形式打印工具调用，被归一化解析器"侥幸"转正。两层 bug 互相掩盖。
**教训**：同功能的多路径实现（complete/stream）必须共享参数构造；静默降级（DSML 归一化）会掩盖上游缺失——**当容错机制频繁触发时，它在替某个真 bug 挡枪**。
**防回归检查**：
- [ ] 改 provider 参数构造时，complete 与 stream 逐字段对照
- [ ] 若 DSML 退化率突然下降→警惕（可能不是变好，而是 tools 根本没传）
- 回归测试：`providers/__tests__` 的「stream 透传 tools」断言（拦截桩捕获实际参数）

<a name="reg-02"></a>
## REG-02 · 流式重试不重置累积缓冲（P1）

**根因**：`withRetry` 闭包内 `full`/`toolAcc`（anthropic: `text`/`toolBlocks`）跨尝试累积。重试仅在 `!delivered` 时发生，但"内容被 DSML 扣留"或"工具分片已到达"都不算 delivered → 第二次结果 = 半截①+全文②。
**教训**：重试闭包要重置**全部**跨尝试状态，不止是显示缓冲。写重试时列出所有 `let` 声明逐一对照。
**防回归检查**：[ ] 新增流式 provider 时，重试闭包第一行重置所有累积变量
- 回归测试：providers 测试「重试后 full/toolAcc 无拼接」

<a name="reg-03"></a>
## REG-03 · 压缩切开工具调用组（P1）

**根因**：`compressIfNeeded` 按 `keepRecent` 条数切片，边界落在 assistant(toolCalls) 与 tool 结果之间 → 孤儿 tool 消息 → 两家 API 都 400 → run 从此每轮失败。
**教训**：消息数组是**配对结构**（assistant.toolCalls ↔ tool.toolCallId），任何切片/裁剪/过滤必须按"组"为单位。
**防回归检查**：[ ] 改消息历史的任何裁剪逻辑时，确认 recent 首条不是 role:'tool'
- 回归测试：context-window 测试「边界落在工具组内时向前扩展」

<a name="reg-04"></a>
## REG-04 · 取消时 checkpoint 毒化续接（P1）

**根因**：取消发生在工具执行中，messages 末尾是"assistant 带 toolCalls 但无 tool 结果"，原样落 checkpoint；`continueSession` 把它种进下一次请求 → API 400 → 该会话永久续接失败。
**教训**：**落库的中间状态必须对"下次读取"合法**，不只是"当前写操作合法"。写 checkpoint 前问一句：这个状态再次加载后能直接用吗？
**防回归检查**：[ ] 取消/失败路径落库前，修剪悬空的 toolCalls / tool 消息（`sanitizeSessionHistory`）
- 回归测试：run-engine 测试「取消后 checkpoint 不含悬空 toolCalls」

<a name="reg-05"></a>
## REG-05 · 公文技能没解 stdin 包装（P1，用户发现：文档只有日期）

**根因**：执行器契约是 stdin = `{input, context}` 包装（AUTHORING_PROGRESS.md 有文档），official-document-generator / official-doc-expander 直接把 stdin 当输入解析 → 所有字段为空。scrape.py 是正确范例。
**教训**：**协议契约靠"照抄现有实现"传播必然漏** —— 新技能脚手架要从模板生成，而不是从记忆手写。
**防回归检查**：
- [ ] 新技能脚本第一行 stdin 解析：`payload.get('input', payload)`
- [ ] 写完技能必须带真实子进程冒烟（走 SkillExecutor，不是手动 echo）
- 回归测试：技能端到端测试（最小 SKILL.md + 脚本子进程）

<a name="reg-06"></a>
## REG-06 · emit_progress/emit_log 签名漂移（P1，审查发现）

**根因**：SDK 签名 `(phase, message, step, percent)`，脚本按旧想象 `(10, 100, '消息')` 调用 → 解析器丢弃非法字段，进度事件全是垃圾；`emit_log('error', msg)` 反转 → 真实错误信息丢失。
**教训**：双语言 SDK × 多脚本 = 高漂移面。**给 SDK 补冒烟测试（Python 侧）**，脚本 PR 必须带进度协议输出样例。
**防回归检查**：[ ] 脚本里的 emit_progress 首参必须是字符串 phase（grep `emit_progress\(\d` 应为 0 命中）
- 回归测试：`grep` 型约定测试（CI 可跑：正则扫描技能目录）

<a name="reg-07"></a>
## REG-07 · AI 编排输出零信任（P1，用户发现：无效 URL [object Object]）

**根因**：编译器把 JSON Schema 写进 input 默认值、引用编造的输出键（markdown vs content）。LLM 输出直接进执行链。
**教训**：LLM 产出 = 不可信输入。**每一层都校验，失败给可操作的错误信息**（不是 [object Object]）。
**防回归检查**：[ ] 编译器提示词规则 / DSL 校验器启发式 / 运行时类型守卫三层都在（缺一即回归）
- 回归测试：dsl「schema 形状默认值拦截」、graph-run-service「类型守卫快失败」、compiler「引用不存在技能/输出键」

<a name="reg-08"></a>
## REG-08 · 路由双层包装 body（P1，真机 DoD 才暴露）

**根因**：路由调 `fireWebhook(id, { body })`，服务签名第二参就是 body 本体 → 变量永远替换不上。单测直调服务层所以测不出。
**教训**：**单测直调会绕过调用层**（路由/适配器/middleware）——关键 API 必须有一条走完整 HTTP 栈的测试（fastify inject）。
**防回归检查**：[ ] 新路由 = fastify.inject 端到端测试，而非直调服务
- 回归测试：trigger.routes 的 fastify inject 用例（覆盖变量注入）

<a name="reg-09"></a>
## REG-09 · seq 计数器重启归零（P1，DoD 实测发现）

**根因**：进程重启后内存 `seqCounters` 从 0 起，新事件覆盖已持久化事件（seq 是 (run_id, seq) 主键）。
**教训**：**任何"内存计数器 + 持久化唯一键"组合，启动时必须从库里播种**（惰性 seed 首触生效最稳，覆盖所有发射路径）。
**防回归检查**：[ ] 新增事件/序列类计数器时，nextSeq 首触从持久层 max() 续接
- 回归测试：graph-run-service「重启后 resume 事件 seq 严格递增」

<a name="reg-10"></a>
## REG-10 · 上传文件状态永不清理（P2，用户发现）

**根因**：修"上传后消失"时把状态改成永不清理（矫枉过正），每轮对话重新注入全部历史文件。
**教训**：**任何"保留状态"的修复都要同时回答"何时清除"** —— 状态生命周期三问：谁创建？谁消费？谁销毁？答不出第三个就是 bug。
**防回归检查**：[ ] UI 暂存态（chips/草稿/选中项）必须有明确的清除时机（发送后/新建/切换）

<a name="reg-11"></a>
## REG-11 · 上下文偏置压过能力清单（P2，用户发现：绑工作区后"无法联网"）

**根因**：绑工作区后系统提示充满文件规则、工具列表 17→24，模型从上下文推断"这是本地文件任务"而拒绝联网——工具明明在列表里。
**教训**：**给模型的规则要显式对抗上下文偏置**（"即使绑定了工作区，web 工具始终可用"），不能假设模型会平权看待工具列表。
**防回归检查**：[ ] 新增工具类目时，检查系统提示是否有对应的存在性声明

<a name="reg-12"></a>
## REG-12 · Web 双通道事件合并无序（P2，审查发现）

**根因**：REST 回放与 SSE 实时事件按到达序合并，旧事件后到会把 UI 状态回退（清单变旧/工具卡复活转圈）。
**教训**：事件驱动 UI 的合并必须**按业务序号（seq）定序**，不按到达序。
**防回归检查**：[ ] 改 useRunStream/useTaskStream 合并逻辑时，确认 seq 排序仍然成立
- 回归测试：web 端 deriveRunView 纯函数测试（乱序事件输入 → 正确终态）

## REG-13 · 批量 patch 脚本断言失败 = 未写盘，但后续 tsc 通过造成误判（工作流，2026-10-04 审查时发生）

**现象**：P0 修复脚本里 `assert old in s` 在第二段失败抛异常，第一段的修复**从未写盘**；随后跑 tsc 通过（因为什么都没改当然通过），误以为修复成功。直到写回归测试才发现 stream() 仍然丢 tools。
**教训**：**验证修复必须验证"行为变化"而非"过程没报错"** —— tsc 通过只说明代码合法，不说明修复存在。修 P0 这类关键问题必须立刻配一条会失败的测试（先红后绿）。
**防回归检查**：

## REG-14 · cron OR 语义误判（终审发现）

**根因**：`domRestricted = !has(0) || !has(31) || size<31` —— DOM 取值域是 1-31，`0` 永不在集合里，`!has(0)` 恒真 → domRestricted 恒真 → `0 9 * * 1`（每周一）走 OR 分支 → 每天触发。反向用例（`0 9 1 * *` 每月1号）恰好走 AND 分支是对的，掩盖了 bug。

<a name="reg-22"></a>
## REG-22 · 安全靠"黑名单"而不是"边界"（P0，审计发现）

**现象**：code-exec 的"沙箱"是一张 import 正则黑名单。真实执行验证：`from os import environ` 打印出集成令牌；`pathlib` 写文件成功；`from subprocess import run` 起了子进程；`sqlite3` 建了库文件；`os.system('echo pwned')` 执行了命令。模型写的代码还拿着整份技能环境变量。
**根因**：黑名单枚举的是"写法"，而写法无穷；真正要管的是**动作**（打开文件 / 起进程 / 连网络）。另外技能工具从不声明效果，"入参是数据"和"入参是模型代码"的技能在系统眼里完全一样。
**修复**：边界做在解释器内部（审计钩子拦截动作 + 拒绝查找器 + 逐出受限模块 + 清环境变量），启动自检 fail-closed；Python 子进程只拿 3 个系统目录变量；技能清单新增 `accepts_code` / `sandboxed`，声明接收代码却没有沙箱的技能直接拒绝执行。
**修复过程中被实测纠正的四个想当然（比 bug 本身更值得记）**：
1. 审计钩子的 `import` 事件**只覆盖 `import` 语句**——`importlib.import_module('winreg')` 不触发任何审计事件（3.9.6 实测）→ 必须再加一层导入查找器。
2. `ctypes.windll.*` 在 3.9 上不触发审计事件 → 它不能靠"动作级拦截"，唯一安全的处理是**绝不让它进进程**。
3. `site.getusersitepackages()` 在非隔离模式返回的是**字符串**——按可迭代对象遍历，路径被拆成 30 个单字符"根"。我据此推断"整盘可读"，实测**不成立**（短前缀规范化后是 `c:\\`，没有任何真实路径以它开头）；真实后果只是文本脱敏被搅碎。**严重程度要靠测量，不能靠推断**——两个方向都是。
4. `code.__new__` / `function.__new__` 是任何模块加载编译都会触发的正常事件，列入拒绝名单会把标准库自己拦掉。
**教训**：边界做在动作层；白名单条目要校验形态（够长的绝对路径），否则拒绝执行；自检里要有"能抓住这类事故"的探针，并用**变异验证**（把事故写法注回去，测试必须变红）确认探针有效；能力范围与局限如实写进文档。
**防回归检查**：
- [ ] 任何执行模型代码的技能必须声明 `accepts_code` + `sandboxed`（仓库清单扫描测试守着）
- [ ] 改前导后跑 20 条沙箱测试（直接启动真实技能脚本），安全类改动再做一次变异验证
- [ ] 新增"可信根"来源时，先打印它规范化后的形态再决定
- [ ] 声明的局限要如实：解释器级隔离不是容器；第三方计算库在导入时自身会加载受限模块，沙箱内不可用（历史 447 次调用中用到它们的为 0 次）

## REG-33 · 正则的"分支"写成了"字符类"（P2，审计发现）

**现象**：自评的"任务规模"判断 `/[并且|以及|然后|同时|;|；|1\.|2\.]/` —— 方括号里 `|` 与每个汉字都只是单个字符，等于"出现 并/且/以/及/然/后/同/时/;/；/1/./2 任意一个就算大任务"。带版本号、日期、网址的目标几乎全部中招，简洁的回答被扣"长度不成比例"。

**现象**：`coral compact` 把旧格式 checkpoint 迁移成去重格式时，用 `.all()` 一次性把全部内联 checkpoint（每条带整份消息快照）读进内存——最需要压实的库正是迁移时内存占用最高的时刻。补测试时又发现：每条写入都是独立事务（各落盘一次），450 条小 checkpoint 要十几秒。这个迁移函数此前没有任何测试。
**根因**：读没有分批，写没有合并事务。
**教训**：**大批量迁移 = 按主键分批读 + 每批一个事务**。另外一条关于测试自身的教训：补测试时第一次超时，7 秒其实花在"测试夹具逐行准备数据"上——**测试超时不一定是被测代码慢，先量夹具**。
**防回归检查**：
- [ ] `.all()` 读可能很大的表 → 改 keyset 分页（`WHERE rowid > ? LIMIT ?`）
- [ ] 循环里的逐条写入 → 包进事务
- [ ] 用例数据量要超过一个批次，并覆盖"不满一批"的尾批
- 回归测试：`store/__tests__/checkpoint-migrate-batches.test.ts`

## REG-43 · 两个派生工具各拿一个计数器，"共用计数"从未生效（P1，体检取数时发现）

**现象**：`run-engine.buildTools` 给 `agent_spawn` 和 `team_spawn` 各传了一个新建的 `{ count: 0 }`。报错信息写着"含 agent_spawn 与 team_spawn 共用计数、上限 8"，实际各算各的——一个任务最多派生 16 个。历史数据对得上：有任务成功派生 15 次。设计注释与 `SpawnDeps` 的文档都写着"run 级共享"。
**根因**：同一个"共享"依赖在两个调用点各写了一遍字面量，没有单一来源；测试只覆盖工厂层（显式传入同一个计数器），装配层没有测试。
**教训**：**"共享"的东西只创建一次**。凡是在多个调用点各写一遍的字面量依赖，默认怀疑它们本该是同一个对象；说明书 / 提示语里写的行为，要有测试证明它真的成立。修正接线时默认值不缩小现有能力（上限默认取修复前实际可用的总量，并做成设置项）。
**防回归检查**：
- [ ] 多个组件声明"共享"某个状态 → 该状态只在装配处创建一次
- [ ] 装配层（`buildTools` 这类把零件接起来的地方）也要有集成测试，不能只测零件
- 回归测试：`kernel/__tests__/spawn-quota.test.ts`、`services/__tests__/run-budget-settings.test.ts`

## REG-44 · 技能说明书承诺的行为从未实现；正文提取遇嵌套容器提前截断（P1，体检取数时发现）

**现象**：`web-reader` 的 SKILL.md（v1.1.0）写着"网络失败返回分类错误 + 可重试标记""内部退避重试""默认桌面 UA""按 max_chars 截断""降级不报错"，脚本却一直是最初的简版：裸 `fetch`、失败只回一句 `fetch failed`。实测该技能 56% 的调用失败，调用方拿到的是"不可重试的脚本错误"，于是对同一地址反复硬撞。顺带发现 `skills/_lib/readability.mjs` 用惰性正则取容器内容，遇到嵌套 div 在第一个内层 `</div>` 就收口——命中的"正文"只有开头一小截，之后的内容静默丢失。
**根因**：**说明书改了，实现没跟上**——那次提交只改了 SKILL.md（+67 行），脚本自创建起没有动过；技能没有"说明书 vs 实现"的契约测试。提取库则是用正则做需要配对的事。
**教训**：文档写下的行为就是契约。改说明书的行为章节时必须同步改实现，并补一条"把脚本当进程跑"的黑盒测试（喂 stdin、读 stdout）逐条核对。成对标签之间的内容要按嵌套层数配对（`balancedEnd`）。
**防回归检查**：
- [ ] 改 SKILL.md 的"网络行为 / 输出"章节 → 同步改脚本，并更新黑盒测试
- [ ] 脚本失败时整个返回值只有 `error` 一个键（技能执行器据此判定为逻辑失败），error 是一行 `[类型] 说明 — 下一步`
- [ ] 用正则取"成对标签之间的内容" → 改为按层数配对
- 回归测试：`skill-runtime/__tests__/web-reader-script.test.ts`、`skills/_lib/readability.test.mjs`

## REG-45 · 两个"限制模型"的方案会误伤高难度任务（工作流，上线前否决）

**现象**：体检报告建议"空回答重询时不带工具、降低推理强度""到上限就把派生工具从列表里拿掉"。用户指出这会伤到高难度任务。取数验证：50 次空回答里 45 次是推理写满输出上限，多发生在任务前几步——拿掉工具会把它逼成没做完就仓促作答。"用过的工具从列表里消失"在严格的接口上会被拒（历史里还有该工具的调用记录），也会让缓存前缀失效。
**根因**：把现象（空回答、反复派生）直接当成"模型不听话"去限制——没有先分清成因，没有推演对正常路径的副作用，也没给用户留调节余地。
**教训**：**限流类改动先问三件事**——限制的是"无效行为"还是"正常行为的尾部"？正常路径会不会被误伤？用户能不能自己调？本条的落点：思考溢出 → 加码不减码（放大输出额度、保留工具、提示语只说"继续"）；派生额度 → 可设置 + 提前写明 + 用完只拒绝不消失。
**防回归检查**：
- [ ] 任何"收紧模型行为"的改动 → 先用数据确认现象的成因分布
- [ ] 任何"动态改工具列表"的想法 → 查接口对历史调用的校验与缓存前缀
- [ ] 修正接线类缺陷时，默认值不缩小现有能力；要收紧交给用户设置

## REG-46 · 真机测试任务落进评测会话（工作流，本轮发生）

**现象**：浏览器实测时对话页自动选中了最近一次会话（恰好是评测会话），我点的"新建"被异步加载完成的会话列表覆盖，测试任务带着 93 条评测历史跑了起来，落在 `gaia-eval-session` 里。
**根因**：界面有异步的"自动选中最近会话"；我的自动化只看了标题就继续操作，没有校验"新建"是否生效（应看会话上下文指示或直接查库里的 session_id）。
**教训**：真机验证前**先确认落在哪个会话 / 工作区**；异步加载之后的每个动作都要读一次状态再继续；测试数据测完立刻按 run id 精确删除，并核对级联清理（runs / events / checkpoints / checkpoint_messages / search_docs）。
**防回归检查**：
- [ ] 真机测试创建的 run → 记下 run id，测完删除并核对残留为 0
- [x] 对话页自动选中时跳过自动化会话（规则取自服务端，运行列表带 `automation_session` 标记，前端不另写一份）；只有自动化会话时停在新建任务
- [ ] 仍待处理：用户手动点开一个评测会话后直接输入，新任务照样会续接到它——是否改为自动开新会话，留给用户决定

## REG-47 · 网页结果的体积靠估算记账，超出预算（上线前发现）

**现象**：网页转成可读内容后的结果，在 996 篇真实存档上有 84 篇超过内联预算、29 篇超过工具的结果上限（会被整份转存成一条摘要）。单元测试没有发现。
**根因**：链接大小按"文字 + 地址 + 固定开销"估算，实际序列化后多出约两成（标记字段、转义字符）；图片、元信息、结构化数据只有条数上限，没有总量上限；另有一组常量让长段结构化数据永远放不进预算。
**教训**：预算记账一律用**序列化后的实际字符数**；每个字段都要有总量上限；用真实存档整体复测最大值，而不是只看构造出来的用例。
**防回归检查**：
- [x] `http.test.ts`「样样都大的页面」：总体积不超过预算，且正文开头保住下限（证明不是靠最后一道保险削正文来凑数）
- [x] 换行极多页面的记账、结构化数据按序列化体积截断，各有断言
- [ ] 新增内联字段时：加进记账，并在存档上复测最大值

## REG-48 · 链接预算过小、"导航"判定埋掉实用链接（上线前发现）

**现象**：链接只给固定的 5000 字符，模型只看得到前三十来条，而 72% 的真实页面超过 30 条；"正文 / 导航"分两份后，模型真正点开的链接里有 33% 落在名额更少的那一份；真机上页面开头的站内菜单又把正文链接挤出了预算。
**根因**：把"导航类链接"当成了同一类，实际上至少有两类可靠程度不同的链接（站内分类、翻页与站点菜单）；预算规则上线前没有用历史轨迹量过两头。
**教训**：淘汰 / 保护类规则先用真实数据量两头（哪头是噪声、哪头是路）；放不下时给出**准确的续读位置**，证据记录里的顺序要与内联顺序一致。
**防回归检查**：
- [x] `http.test.ts`「链接密集页面」一组：预算放宽、三级顺序、导航保底、"前一段不跳着挑"、续读位置的独立校验
- [x] `html-text.test.ts`：`list` / `nav` 分开标记；收录上限与 `linksTruncated`
- [ ] 链接分级是启发式的（见 README 局限性）；改折叠或分级规则时，用存档回放复测"被点开的链接看得见多少"

## REG-49 · 新工具写完才验证设想，整份撤销（工作流，上线前否决）

**现象**：围绕一个很显眼的统计数字设计了一个新工具，单元测试全绿、各处接线都接好了，才拿历史轨迹回放去问"它能不能挑出模型真正要的页面"——基本不能，于是代码与接线全部撤销。
**根因**：把"一个相关的统计数字"直接当成了需求；先实现、后验证。
**教训**：测试全绿只证明实现符合设想，不证明设想符合现实。**验证设想要在写代码之前**：拿历史轨迹回放（"如果当时就有它，结果会不会不同"），再决定做不做。
**防回归检查**：
- [ ] 新工具 / 新策略：先回放、后实现；回放脚本与结论留档

## REG-50 · 沙箱自检按路径长度判"可信根"，Linux 上系统自带的 Python 被整体拒绝（CI 暴露）

**现象**：code-exec 的沙箱自检在 Linux 上报"可信根目录异常: '/usr'"，所有代码执行被拒绝；CI 的两个 Ubuntu 作业因此失败，Windows 与 macOS 通过。本地只在 Windows 上验证，没有发现。
**根因**：自检用"路径长度不少于 12"当作合法性判据，本意是拦截被拆成单字符、只剩盘符的白名单；但 Linux 系统自带的 Python，解释器目录就是 `/usr` 或 `/usr/local`，完全合法却被判成异常。判据写成了"像不像坏数据"，而不是"是不是坏数据"。
**教训**：校验规则要描述坏数据的**确切结构**（不是绝对路径、指向文件系统根），不要用长度、外观这类代理特征；带平台差异的代码（路径、解释器位置）要有能在任意平台上验证那种差异的测试——把规则抽出来，喂入另一平台的典型值。
**防回归检查**：
- [x] `code-exec-sandbox.test.ts`「可信根目录的自检按结构判，不按长度判」：把前导脚本当模块加载，在 Windows 上验证 `/usr` 这类短前缀
- [ ] 诚实边界：可信根是 `/usr` 时，沙箱内代码可只读打开整个 `/usr`（系统文件，本就对所有用户可读）

## REG-51 · 推送后不核对 CI，Linux 上的失败挂了一个版本（工作流）

**现象**：一次推送后只在本地（Windows）跑过测试，没有看远端 CI；两个 Ubuntu 作业失败了一天多，直到下一次推送后查看才发现。
**根因**：收尾清单里没有"推送后核对 CI"这一步；本地环境单一，平台相关的问题只有 CI 能暴露。
**教训**：推送后必须核对 CI 的**每一个作业**。日志下载需要管理员权限时，公共仓库的检查结果注释接口就能看到失败断言，不需要登录。
**防回归检查**：
- [x] 收尾清单加入"推送后逐个作业核对 CI"；连续启动外部进程的测试给足时间上限（进程启动慢会被误判成失败）
